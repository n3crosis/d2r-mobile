# NSP extraction runtime

The browser extraction worker uses pinned hactool source at `1d64a83450e025622f3468c28fc4164dad2c5ef6`, compiled with Emscripten 4.0.20. Build static assets with `bash web/toolchain/nsp-extract-spike/build-wasm.sh`; end users do not install an SDK. See [production flow](../../PRODUCTION_FLOW.md) for orchestration and [local tests](../../TESTING.md) for optional extraction checks.

## Non-BKTR ExeFS boundary

The API provides `open(index,"program-exefs")` / `nsp_open_exefs` for a signed Program NCA with exactly one supported PFS0 ExeFS section. It verifies the fixed retail RSA-PSS signature, every present section-header hash, section extents/non-overlap, and the selected PFS0 hash hierarchy before exposing entries. It requires `main` with NSO0 magic and `main.npdm` with META magic. These markers identify ExeFS; they do not establish game-version compatibility, full NSO/NPDM validity, runtime permissions, or a bootable program.

Unknown crypto, ambiguous PFS0 selection, unsupported selected-section encryption, or malformed directories are rejected. The patch reader permits an unselected BKTR RomFS section alongside independently verified ExeFS. **RomFS contents are not extracted or authenticated by the ExeFS-only operation.** A standard unused RomFS section may coexist, but only its signed header/hash/range is checked. The separate legacy patch operation is described below; there is no signature bypass for synthetic tests.

`hashInput(index)` returns an independently computed SHA256 hex digest of the entire selected raw Blob, supporting content inventory checks. It closes the current member directory, which must be reopened afterward. `hashEntry(index)` returns SHA256 of one open decrypted member for the existing exact `main`/`sdk`/`subsdk0` version gate. Both use the same bounded 64 KiB incremental hashing helper as section verification. The Program PFS0 payload is not limited to 16 MiB or copied into memory; hash tables and directory metadata remain limited to 16 MiB. Verification is synchronous within the Worker, so cancellation during a long hash/verification requires terminating the disposable Worker rather than waiting for another message to execute.

PFS0 directory handling rejects duplicate names, overlapping nonempty members and failed-open state.

## Non-BKTR RomFS boundary

`openRomfs(index)` returns a frozen `{size: bigint, readAt(offset: bigint,count: number)}` reader only after fixed retail RSA-PSS signature verification, all present section-header hashes and ranges, and the selected section's complete six-level IVFC hierarchy verification. Offsets are relative to the final IVFC data level, and reads are limited to 64 KiB. This synchronous dedicated-Worker reader can be passed to `indexRomfs` in `web/romfs-tree.mjs`, which awaits reads and validates the separate directory/file tree. A reader expires on another mount, inspect, open, key load, full-input hash or disposal. Do not mutate the mounted files or expose the underlying WASM module to other callers.

Supported layout is legacy IVFC `0x20000`, seven levels including the signed root, a 32-byte master hash, six nonoverlapping data/hash extents and block exponents 5–24. Each level is checked against its already-verified parent; final partial blocks are zero-padded for SHA256 as in pinned hactool `nca_process_ivfc_section`/`nca_section_check_external_hash_table`. Hashing uses a 64 KiB scratch buffer, not a full RomFS copy. The root is authenticated through the signed NCA's section-header hash, not trusted from a caller. The final RomFS header must have the standard 80-byte header size; tree structure validation belongs to the JS reader. Full verification is synchronous and can be slow for large images; cancellation during it requires terminating the Worker.

All BKTR, sparse, compressed, newer metadata-hash/skip-layer-hash extensions, unsupported IVFC layouts, ambiguous sections, and selected XTS encryption are rejected. This is not patch/base merging. Only the selected RomFS hierarchy is verified; opening RomFS does not verify the separate ExeFS payload. Exact executable compatibility checks remain necessary; the browser skips full base/update NCA hashing.

Format evidence: pinned [hactool ivfc.h](https://github.com/SciresM/hactool/blob/1d64a83450e025622f3468c28fc4164dad2c5ef6/ivfc.h) and [nca.c](https://github.com/SciresM/hactool/blob/1d64a83450e025622f3468c28fc4164dad2c5ef6/nca.c). No additional upstream code or license dependency is introduced.

## Authenticated legacy BKTR boundary

`openPatchedRomfs(baseIndex,patchIndex)` now has a native implementation using simultaneous authenticated base/patch contexts, bounded relocation/subsection parsing, split CTR-Ex reads and mandatory patch-root IVFC verification over the merged virtual section. It returns the same bounded, generation-guarded final-RomFS reader. Modern/unknown variants remain rejected. See [Bounded BKTR reader](README.md#bounded-bktr-reader) for supported layouts and source mapping.

The browser uses fast content checks: it skips full base/update NCA hashing and the full RomFS integrity scan while retaining signed-header and package-structure checks. The small known Warlock add-on NCAs are always hashed and checked against their content IDs and CNMT data digest. Its Meta and PublicData headers may lack retail signatures; this exception never applies to executable base/update content and does not establish retail provenance. Full base/update hashing has no browser option or URL override. The strict API and its IVFC fixture remain available for independent callers.

## Extraction worker integration

`extraction-worker.mjs` and `extraction-engine.mjs` connect production NSP cataloging, NCA SHA256 measurement, CNMT parsing and internal base/patch selection to token-bound ExeFS and RomFS reads. Selection requires the exact known D2R base/update/Warlock package evidence through the expansion policy. The known Warlock add-on gets full NCA hashes and CNMT consistency checks even in fast mode; its Meta opener has a narrow unsigned-header exception. Unknown DLC and multi-program layouts reject. Known unlock-only DLC is not a Program RomFS overlay or an ownership claim. See [Local extraction Worker protocol](README.md#local-extraction-worker-protocol) for the narrow protocol and streaming-lifetime requirements.

## Implemented batch and public interface

- `build-wasm.sh`: obtains exact hactool commit, applies `prepare-source.py`, builds bundled mbedTLS and a modularized 256 MiB-maximum WASM module. No CLI `main` is linked. Distribution includes source-embedded notices and checksums.
- `prepare-source.py`: fail-closed, exact-source transformations for static parser-line wiping, title-key realloc wiping, title-key stack temporary wiping, the critical wasm32 `fseek` to `fseeko` correction, early unsupported-header rejection, and initialized NCA2 section-header detection. `quiet.h` removes upstream formatted diagnostic calls at compile time before their arguments are formatted.
- `boundary.c`: explicit `/secret/prod.keys` and `/secret/title.keys` only; no HOME/XDG search. Exposes header inspection, raw PFS0 fixture reading, and Meta-NCA PFS0 access. Base/update Meta access requires a valid fixed header signature, section-header hash and complete bounded PFS0 hash hierarchy. The separate Warlock Meta entrypoint accepts the known title's unsigned header while retaining section and PFS0 hash checks.
- `browser-boundary.mjs`: `createBoundary(factory)` must execute in a fresh dedicated Worker. `mount(blobs)` creates read-only WORKERFS views, `loadKeys(prodBytes,titleBytes)` takes mutable arrays and wipes them plus memory-only files, `inspect(index)` returns public header fields with signature validity, `open(index,"meta")` opens verified metadata, `entry(index)` describes one member, `read(index,bigintOffset,count)` returns at most 64 KiB, and `streamEntry(index,sink,signal)` applies awaited backpressure. `dispose()` wipes native state and linear memory; terminate the Worker afterward. No complete output file is accumulated in MEMFS or a Blob. Use sliced NCA Blobs from the production NSP input catalog, not this spike's JS PFS0 parser.
- `smoke-worker.mjs`: synthetic crypto, explicit mutable key staging/cleanup, real Blob/WORKERFS PFS0 reading, 64 KiB output backpressure, cancellation, path rejection and a sparse synthetic FS node exercising actual WASM seeks beyond 4 GiB. The sparse test is not a 5 GiB real-Blob/platform performance test. No package or real key fixture is used.

The Meta API caps its PFS0 and hash metadata at 16 MiB and accepts one supported CTR or plaintext section. `synthetic-pfs0` is a test-only raw-container mode, not the production catalog validator. On a WASM abort, terminate the worker rather than reuse it.

## Key lifetime and logging requirements

Use a fresh Worker/module per conversion. Read key files as mutable byte buffers, never File.text()/TextDecoder into long-lived JS strings or CLI `--titlekey` arguments. Transfer ArrayBuffers to the Worker (detaching sender ownership), parse into bounded mutable buffers, and wipe raw input promptly after parsing. Explicitly wire both selected files into the parser, bypassing ambient HOME/XDG lookup. A temporary memory-only file wrapper may ease initial integration but must be wiped and unlinked; it must never be synchronized to persistent storage.

Patch parser diagnostics before any real user input is accepted. `extkeys.c` contains warning paths that print raw key/value strings, and upstream options alone are not a comprehensive confidentiality boundary. Suppress all raw stdout/stderr at the bridge; return only typed error codes with public descriptions. Never report buffer contents or dump a WASM memory image. Disable telemetry/error-report payloads and network operations in the extraction Worker after its static code loads.

Add explicit compiler-resistant zeroization for parser line buffers, temporary key bytes, keysets, known title-key arrays and cryptographic contexts before free on success/failure/cancel. Audit realloc and stack temporaries. On cleanup, destroy the fresh module and terminate Worker. JavaScript/browser garbage collection and process memory cannot guarantee forensic erasure; promise no intentional uploads/logging/persistence, not impossible memory secrecy. Run a canary-key test that asserts no bytes reach network, console, storage, crash messages, or final artifacts.

## Bounded BKTR reader

The bounded JS relocation parser/planner is an independently usable **untrusted
routing primitive**, not a decryption or authentication API. Synthetic fixtures do
not establish compatibility with signed retail base/update inputs.

### Exact upstream mapping

All references are to official hactool commit `1d64a83450e025622f3468c28fc4164dad2c5ef6`:

- [bktr.h](https://github.com/SciresM/hactool/blob/1d64a83450e025622f3468c28fc4164dad2c5ef6/bktr.h): 32-byte BKTR descriptors (offset, size, magic, version, entry count, reserved); 16 KiB root and bucket nodes. A root has 16-byte header then 64-bit bucket boundaries. Relocation buckets have 16-byte header then packed 20-byte `{virtual_offset,physical_offset,is_patch}` records. Subsection buckets have packed 16-byte `{offset,reserved,ctr_value}` records.
- [nca.c](https://github.com/SciresM/hactool/blob/1d64a83450e025622f3468c28fc4164dad2c5ef6/nca.c), `nca_process_bktr_section`: relocation table immediately precedes subsection table, whose end is section end. Upstream reads both with ordinary CTR before installing them as virtual routing state, adds synthetic sentinels in memory, then verifies IVFC over the merged address space.
- `nca_section_fseek` and `nca_section_fread`: base relocation physical offsets address the **complete decrypted base section**, not the final RomFS file-data layer. Patch relocation offsets address patch physical section storage. Reads split at relocation boundaries, and patch reads also split at encryption-subsection boundaries. The existing `openRomfs` reader deliberately exposes only the final level and is therefore not a valid base-section adapter.
- `nca_update_bktr_ctr`: the low 64 counter bits encode the absolute file offset divided by 16, big endian; bytes 4–7 encode the subsection's 32-bit generation value big endian. Bytes 0–3 retain the section secure value. Unaligned AES reads need block-aligned decryption and slicing. Metadata table reads use the ordinary section counter generation.

The modern encrypted/plaintext subsection discriminant is confirmed by official [Atmosphere AesCtrCounterExtendedStorage::Entry](https://github.com/Atmosphere-NX/Atmosphere/blob/master/libraries/libstratosphere/include/stratosphere/fssystem/fssystem_aes_ctr_counter_extended_storage.hpp); no Atmosphere implementation code is copied.

The legacy upstream parser allocates caller-sized tables, relocates buckets in place, inserts sentinels, and may terminate on malformed lookups. The browser must not call that unrestricted path. Table indices, ordering, extents, counts and read splits require independent bounds validation first.

### Implemented safe primitive

`parseRelocations(bytes,{entryCount,baseSize,patchDataSize})` accepts an already-decrypted legacy relocation table capped at 16 MiB. It validates a single root with contiguous 16 KiB bucket nodes, exact node lengths, bucket ranges, first virtual offset zero, strict entry ordering, source flag 0/1, descriptor entry count, and every mapped physical extent against its source limit. It snapshots records into frozen metadata so later changes to input bytes do not change the plan. Unsupported tree layouts fail rather than guessing.

`planRelocationRead(table,offset,count)` returns frozen base/patch physical read spans, splitting across virtual relocation boundaries, capped at 64 KiB total. All offsets remain BigInt. Synthetic tests cover base/patch/base crossing, physical offsets above 4 GiB, EOF, malformed counts/order/source flags and out-of-range mappings. This primitive does not read or decrypt source content and does not assert that the table is authenticated. It must remain internal to a future verifier, never a public unchecked extraction path.

### Native legacy patch path

`openPatchedRomfs(baseIndex,patchIndex)` / `nsp_open_patched_romfs` now opens and verifies the base RomFS first, transfers that context into separate owned storage, authenticates the patch header, and selects its unique BKTR RomFS section. Both fixed retail RSA-PSS signature checks and section-header hash/range checks remain mandatory. The base and patch use separate file/AES contexts, wiped/freed together on close or failure.

`bktr-reader.h` bounds and validates native relocation and subsection tables without calling hactool's unrestricted BKTR parser. It supports version-1 descriptors, one-root legacy bucket tables capped at 16 MiB each, encrypted subsection entries with 16-byte aligned starts, and exact descriptor/count/physical layout consistency. Modern plaintext subsection flags, sparse/compressed storage, additional tree shapes and unknown formats remain unsupported. The final subsection data range ends at the relocation metadata start, following upstream's explicit sentinel rule; metadata itself is read under ordinary CTR before routing is activated.

The merged reader splits both virtual relocations and physical encryption subsections. CTR-Ex is constructed with the subsection generation, section secure value and absolute file block offset. Unaligned reads decrypt an aligned prefix and return only the requested bytes. All pulls are at most 64 KiB. The strict API checks the complete merged six-level IVFC tree against the master hash authenticated by the patch header before exposing the final RomFS reader. The web packager's fast path skips that second whole-image scan only after measuring each selected Program NCA's full SHA-256 and matching it against authenticated CNMT metadata. It still validates IVFC structure and retains the same generation-lifetime guard. Any error closes both contexts; no partial output or fallback base is returned.

`open(index,"program-exefs")` may now coexist with an unselected BKTR RomFS section. It still verifies only its selected PFS0 content and signed section headers, not the BKTR payload. This permits independently verifying the patch executable without falsely treating it as a merged filesystem. Selecting BKTR as PFS0 or using a patched base for the new merge remains unsupported.

A closed C fixture, exposed only as a no-argument synthetic self-test, constructs public in-memory fixture data and temporary memory-filesystem files, validates malformed table rejection, checks CTR-Ex ciphertext against an independently generated OpenSSL SHA256 digest, reads across base/patch and encryption-generation boundaries including unaligned offsets, and runs the same merged-IVFC verifier. Changed patch ciphertext and wrong base bytes must fail integrity. It always closes every synthetic context and never exposes a reader, accepts a caller root/key/path, or skips production RSA validation. Chromium additionally rejects an unsigned base through the new production patch API. Run the optional local `extraction` profile in [TESTING.md](../../TESTING.md).

### Still required before an end-to-end claim

- Production metadata selection must enforce CNMT application/patch association and independently measured whole-NCA hashes before calling this boundary. The low-level API does not infer association from filenames or assert game-version compatibility.
- Actual signed base/update fixtures have not been supplied or tested. Synthetic success cannot prove compatibility with real game formats or the selected title/version.
- The JS planner is a readable test oracle; production native parsing uses the same field mapping but is not wired through that JS module. Broader malformed-table fuzzing and native/browser parity fixtures remain useful follow-up coverage.
- Unsupported modern variants remain fail-closed. No signature bypass, optional verification, unchecked extraction callback or guessed patch fallback is provided.

## Local extraction Worker protocol

This is an internal extraction adapter boundary, not UI enablement or a complete
NSP-to-IPA claim. Synthetic tests do not establish compatibility with valid signed
game base/update fixtures. Use the optional local `extraction` profile in
[TESTING.md](../../TESTING.md) for native and Chromium checks.

`extraction-worker.mjs` statically imports the pinned WASM module, its boundary and the pure engine. No arbitrary source URL, native name, filesystem path or callback may be provided by a message. Input is `{id,operation,payload}` with a monotonically increasing positive safe-integer ID. Exactly one request may be outstanding; callers must await its result before sending another. Success is `{id,ok:true,result}`; failures use `{id,ok:false,error:CODE}` with a fixed allowlist in `extraction-errors.mjs`, never native/parser text. During initialization and RomFS opening, `{id,progress:{stage,completed,total,bytes}}` reports fixed substages and bounded numeric counts, never selected filenames, key names/values or rights IDs. Base and merged IVFC verification each report a percentage of authenticated blocks; the browser read counter reports bytes without a percentage for older runtimes. These events cannot renew the request deadline. Operation errors close the session. Invalid envelope/busy messages are rejected without adding work to an unbounded queue. Cancellation during synchronous hashing must terminate the Worker; do not wait for a cancellation RPC to run.

Operations:

- `initialize({nsps: Blob[],prodKeys: Blob,titleKeys?: Blob})` reads bounded key bytes inside the Worker (an absent title file becomes an empty memory-only input), wipes temporary arrays, uses the production NSP outer-catalog validator, computes every full-NCA SHA256 independently, verifies headers and opens authenticated Meta content before parsing CNMT. Returns `{records,inventory}`. Duplicate content IDs with different measured identity reject; identical duplicates are collapsed. NCZ and malformed NCA names reject. Other ordinary ticket/certificate members are not extracted.
- `select({options})` runs the known D2R expansion policy on retained authenticated records and independently measured inventory, preserving all generic metadata resolver checks. Only `baseVersion`, `patchVersion`, `dlcVersions` options are accepted. It requires the exact D2R application, associated update and known Warlock add-on identities, with the conservative single nonempty Data content at ID offset zero and attributes zero. The add-on remains in required contents and must have both its independently verified full NCA hash/size and an actually signature-verified NCA Data header. Missing/unknown DLC, inconsistent content types and unsupported layouts reject. It currently supports exactly one Program at ID offset zero in each selected base/patch. The known unlock-only add-on is not overlaid onto Program RomFS; no caller ownership Boolean or native-runtime change is introduced. This is local package-input evidence, not legal ownership, purchase or ticket-entitlement verification. Real DLC layout compatibility remains unproven until authenticated packages are supplied. Returns canonical `{selection,token,entries}`, where entries are `{index,name,size,offset}` for the independently verified selected ExeFS. This does not establish executable-version compatibility.
- `readExefs({token,index,offset,count})` returns a transferred Uint8Array, capped at 64 KiB with exact BigInt range checks. Capture/stage required executable members before opening RomFS. Version allowlisting and executable conversion remain separate required steps.
- `openRomfs({token})` opens the authenticated base or supported base/patch merge, revokes the ExeFS token and returns `{token,size}` for the final authenticated RomFS level.
- `readRomfs({token,offset,count})` returns at most 64 KiB. This can back `indexRomfs` and then `createCascLogicalAssets` through a bounded serial RPC client. Generators must receive only this read capability, never the Worker, key/input handles, arbitrary execute function or session controls.
- `dispose({})` wipes native state, drops retained metadata, acknowledges and closes the Worker. The owner must also terminate it on failure, cancellation, timeout, malformed response or disposal failure. There is no resumed-session or persistence path.

The existing coordinator default disposes before generation. Lazy RomFS readers require the separately reviewed opt-in archive-lifetime mode: retain the isolated Worker only through entry streaming, then dispose before final validation/commit and on every failure. No full decrypted RomFS staging is required by this engine. ExeFS and RomFS share one native active context, so opening RomFS makes all previous ExeFS capabilities unusable. The caller must stage only the small required executable subset first, or introduce another independently reviewed context design; concurrent open switching is not supported.

Node tests use an explicitly fake native boundary to test catalog/selection orchestration, key-array wiping, hashes, states, stale tokens and bounds. They are not positive NCA proof. Chromium smoke instantiates the real Worker/module and checks forbidden-operation sanitized failure plus clean disposal; production signature gates remain unchanged. Worker isolation/CSP, local staging and the parent RPC capability wrapper still need integration review before enabling UI generation. Same-origin code is trusted; JavaScript cannot prove complete secret erasure after crashes or browser memory copies.

The expansion-policy integration tests use synthetic CNMT for the known IDs and mock native verification. They assert that missing Meta evidence, wrong whole-DLC hash, unsigned DLC headers and a non-Data NCA header reject, and that the DLC remains in requiredContents without an ownership flag. The generic content-selection parser/resolver remains independently reusable; there is no production worker fallback that omits the known DLC requirement.
